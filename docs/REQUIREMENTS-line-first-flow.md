# 需求規格：LINE 優先流程（LIFF 化）與提醒改版

> 這份文件是給 Claude Code 在 VS Code 實作用的規格書，決策內容來自與店主
> 在聊天中確認過的需求（含一次 ChatGPT 共同討論的結論）。實作過程中若有
> 新的疑問或需要調整規格，請回到原本那個聊天串確認，再更新這份文件。
>
> 這份文件是在 `REQUIREMENTS-auth-payroll.md`（Google 登入／權限／工時
> 試算）之後的下一階段，**不是取代它**，而是改變「員工要怎麼開始使用」
> 這件事。Google 登入、權限模型、工時試算的邏輯本身不變，只是員工端的
> 入口從「開瀏覽器 Google 登入」換成「點 LINE 裡的連結」。

## 背景與問題

Demo 給實際員工看過之後，得到的回饋是「比以前用試算表填還麻煩」
（要先 Google 登入才能填班表）。整理後的根因：

- **管理員的問題已經解決**：試算表不用公開給所有人看、不用自己追誰沒
  填、可以看到重疊班別。
- **但員工的操作成本反而變高了**：以前「打開試算表直接填」一步到位，
  現在是「開網址 → Google 登入 → 選姓名（首次）→ 填班表」。
- 本質上是把管理員的成本轉嫁到員工身上，而不是真的兩邊都變輕鬆。

下一階段的目標：**後端邏輯（權限、寫入試算表、重疊比對、工時試算）
完全不變，只把員工端的操作壓到「點開 LINE 裡的連結 → 選 → 送出」。**

## 一、為什麼選 LINE + LIFF，不是重新做 LINE Login 那條路

之前做的「LINE Login（OAuth 同意畫面）」跟這次要做的「LIFF」是不同
機制，先釐清差異：

| 方式 | 員工看到什麼 | 何時觸發 |
|---|---|---|
| LINE Login（已完成） | 跳出瀏覽器、LINE 的同意畫面 | 每次「連結」操作都要跑一次 |
| **LIFF（這次要做的）** | 從 LINE 裡點連結，直接看到表單，**沒有同意畫面**（除了第一次的一次性授權） | 每次打開都自動識別身分，無感 |
| 純 LINE 對話（Quick Reply／Flex Message） | 完全不離開聊天室 | 適合是非題，不適合「選日期＋選時段」這種複雜輸入 |

**結論**：员工提交班表這個「需要選日期、選時段」的操作，適合用 LIFF
（在 LINE 裡打開的網頁），而不是硬塞進聊天室對話，也不需要每次跳
LINE Login 的同意畫面。

已經做好的 LINE Login 機制不會浪費 —— 它驗證 LINE `id_token` 的後端
程式碼（`oauth2/v2.1/verify`）可以直接沿用在 LIFF 這邊，因為 LIFF 的
`liff.getIDToken()` 回傳的也是同一種 LINE ID Token。

## 二、目標架構：LINE 是「入口與通知層」，Web App 是「畫面層」

這一點也是為了回答「以後要擴充成店舗OS（在庫確認、任務管理）時，
LINE 是不是最佳選擇」這個問題。結論：**LINE 本身不適合做複雜畫面
（表格、清單、輸入），但非常適合做「入口 + 通知 + 身分識別」**。

```
┌─────────────────────────────────────────────┐
│  LINE 官方帳號                                │
│  ・Rich Menu（選單，之後可以放「排班」「庫存」「任務」等按鈕）│
│  ・個人 DM 通知（提醒、狀態變化）              │
│  ・身分識別（LINE userId ↔ 員工）             │
└───────────────┬───────────────────────────────┘
                │ 點 Rich Menu 或通知裡的連結
                ▼
┌─────────────────────────────────────────────┐
│  LIFF 網頁（實際上還是同一個 GitHub Pages 網站） │
│  ・排班希望送出畫面（這次要做的）              │
│  ・（未來）庫存查詢畫面                        │
│  ・（未來）任務清單畫面                        │
└───────────────┬───────────────────────────────┘
                ▼
┌─────────────────────────────────────────────┐
│  Apps Script（後端，邏輯完全沿用現有的）         │
│  ・身分驗證、寫入試算表、重疊比對、工時試算       │
└─────────────────────────────────────────────┘
```

這樣分層之後，以後要加「庫存確認頁」，做法是同一套模式複製一份
（Rich Menu 加一個按鈕 → 開一個新的 LIFF 頁面 → 後端加對應的 API），
不需要每次都重新設計「怎麼識別是誰」。

### 已知限制：LINE 免費方案的通知則數上限

LINE 官方帳號免費方案是**每月 200 則**，而且未來加的所有通知（排班
提醒、庫存告警、任務提醒…）都算在同一個額度裡。這次的「未提交者
個別提醒」（見第四節，一週一次、只發給未交的人）用量很小，但要提醒
自己：**之後每加一種「每天／每人」的通知，額度消耗會快很多**，設計
新功能時要把這個算進去，避免不小心超額被要求付費。

## 三、員工端流程（LIFF 排班提交頁）

### 3.1 新頁面：`frontend/liff-shift.html`

- 取代現有 `index.html` 給**員工**用的角色。`index.html` 的 Google
  登入流程之後只保留給**管理員**用（見第五節）。
- 頁面載入時自動執行：
  1. `liff.init({ liffId: ... })`
  2. 若尚未登入 LIFF（理論上在 LINE App 內開啟時是自動登入的，不需要
     使用者按任何按鈕）→ `liff.login()`
  3. `liff.getIDToken()` 取得 ID Token，送到後端驗證
  4. 後端用「LINE連結」分頁的對照表，把 `userId` 反查成員工姓名：
     - **已綁定** → 直接進入排班表單，不顯示任何登入相關 UI
     - **未綁定** → 顯示「請選擇你的姓名」一次性畫面（沿用現有的
       首次綁定邏輯，只是觸發來源從 Google 換成 LINE）

### 3.2 沿用不變的部分

- 7 天週期（下週一～下週日）的日期選擇
- 早班／下午晚班／晚班／全班的預設時段 + 自訂時間
- 排休
- 「班表反映預覽」的重疊比對（只顯示自己＋重疊到的同事）
- 工時試算（本月累計＋下週預估）
- 寫入試算表的後端邏輯（`submitShift` 等）完全不變，只差身分驗證
  來源從 Google id_token 換成 LINE id_token

### 3.3 新增：「與上週相同」按鈕

- 在表單最上方加一顆「套用上週的班表」按鈕。
- 點下去後，後端讀取該員工「上一週」（即目前這週）每天已提交的
  內容，複製貼到「下週」對應的日期欄位（**只是預填，不會自動送出**，
  員工仍需要檢查並按「送出班表」才會真的寫入試算表）。
- 若上週某天是空白（沒交過），該天維持空白，不強行帶入。
- **實作時的修正**：不需要新增 `getLastWeek`。既有的 `getWeek` 本來就
  吃日期清單，把「這一週」的日期傳進去就是上週的內容，所以這一段
  完全在前端完成，不用重貼 Apps Script。
- **實作時的修正**：規格原本寫「只是預填，不會自動送出」，但這一頁的
  「確認設定」本來就是一按就寫進試算表，沒有草稿狀態。為了不讓同一頁
  出現兩種規則，改成**確認對話框 + 當場寫入**，並且**只填還空著的日子**
  （已經填好的不覆蓋）。

## 四、提醒機制改版：從「群組全員 mention」改成「只提醒未交的人」

### 4.1 現況（要改掉的部分）

- 目前 `remindUnsubmitted()` 是固定時間對「LINE 群組」發一則訊息，
  把未交的人 mention 出來。
- 缺點：全員都看得到誰還沒交（管理員原本就不想讓同事互看班表，這個
  設計跟那個初衷矛盾）、且做法依賴「群組」這個結構，以後要做「個人
  任務提醒」之類的功能不好複用。

### 4.2 新設計：個別私訊

- 條件不變（時間主導觸發器、可由管理頁設定星期/時段）。
- 觸發時，後端一樣算出「下週 7 天內、還有空格的人」名單。
- 但**改成對每個未交的人各發一則個人 DM**（用該員工在「LINE連結」
  分頁裡登記的 `userId`，`push message` 直接發給本人），而不是發到
  群組 mention。
- 訊息內容包含：還缺幾天沒填、一個直接開啟 LIFF 排班頁的連結
  （`https://liff.line.me/{LIFF_ID}`）。
- 未綁定 LINE 的員工（`userId` 未知）如何處理：這種情況理論上不該
  發生，因為員工本來就是透過 LIFF 使用系統、使用當下就會完成綁定。
  若真的遇到未綁定但也未提交的人，暫時**跳過**（不寄送），並在管理頁
  的清單上特別標示「無法提醒（尚未使用過 LIFF）」，方便管理員用其他
  方式（口頭、LINE群組公告）通知。
- 群組訊息**保留**，但用途改成「全店公告」（例如：本週提醒已發送、
  截止日提醒），不再逐一 mention 個人。這部分沿用第五節的「入口/
  通知」角色劃分。

### 4.3 管理頁調整

- **已實作**：「03 LINE 催繳提醒」的試送改成個別 DM，而且**只送給在名單上
  勾選的人**（1〜2 位），不會對全部未交者發出真的催促。
- **已實作**：未提交名單每一列都標「可提醒」／「無法提醒」，無法提醒的人
  （還沒用過 LIFF）不能勾選，下面另外說明要用別的方式告知。

## 五、Google 登入的角色調整：只留給管理員

- **已實作**：`frontend/index.html` 只剩下「振り分け」——員工看到
  「請從 LINE 填班表」＋ LIFF 連結，管理員按「我是管理員」走 Google 登入，
  登入成功就直接導向 `admin.html`。員工用的表單整個移到 `liff-shift.html`。
- `admin.html` 裡原本指向 `index.html` 的員工連結（「前往員工頁面」、
  「切換到員工畫面」）也改成指向 LIFF，店長自己填班表一樣走 LINE。
- `admin.html` 本身不變。

## 六、Rich Menu（為「店舗OS」擴充預留位置）

- 在 LINE 官方帳號設定一個 Rich Menu，目前先放 1 個按鈕：
  - 「📅 提交班表」→ 開啟 `liff-shift.html`
- 其餘按鈕位置先保留、標示「準備中」或暫不顯示，等庫存確認、任務
  管理等功能真的要做時再啟用，不用現在預先做假頁面。
- 這樣做的目的：驗證「LINE 是店舗OS 入口」這個架構本身沒問題，之後
  加新功能只是「多開一個 LIFF 頁 + Rich Menu 多一個按鈕」的重複性
  工作，不需要重新設計身分識別或入口邏輯。

## 七、資料模型變更

在既有「LINE連結」分頁（`姓名 ↔ userId`）之外，這次不需要新增分頁或
欄位，沿用 `REQUIREMENTS-auth-payroll.md` 訂的 C 欄 Email 與既有結構
即可。若要支援「已綁定但無法提醒」的判斷（4.2），可以直接用「LINE
連結」分頁裡有沒有這個人的紀錄來判斷，不需要額外欄位。

## 八、Apps Script 新增／修改的 API

### 8.1 `doGet`

- ~~`action=getLastWeek`~~ → **不需要新增**。既有的 `getWeek` 就吃日期
  清單，前端把「這一週」的日期傳進去即可（見 3.3）。

### 8.2 `doPost`

- `remindUnsubmitted()`（時間觸發，非 API，但邏輯要改）：改成對每位
  未交員工各發一則 `push message`（個人），而非對群組發一則
  mention 訊息。

### 8.3 既有 API

- `whoami`、`submitShift`、`getWeek`、`linkAccount` 等維持不變，
  差別只在於呼叫來源從「Google 登入頁」變成「LIFF 頁」，身分驗證都
  已經是走 LINE id_token 驗證（因為 LINE Login 階段已經做好），不用
  重寫。

## 九、部署／設定注意事項

1. **LIFF App 建立**：在既有的 LINE Login 頻道（或 Messaging API
   頻道，兩者都能掛 LIFF）底下的「LIFF」分頁新增一個 LIFF App：
   - Endpoint URL：`liff-shift.html` 部署後的 GitHub Pages 網址
   - Scope：`profile`、`openid`（不需要 `email`，因為身分識別是靠
     `userId` 對照表，不是靠 email）
   - Size：建議 `Full`（讓表單有完整畫面空間）
   - 取得的 **LIFF ID** 要填進前端設定（新增一個
     `frontend/js/liff-config.js` 或併入既有 `config.js`）
2. **Rich Menu 設定**：LINE Official Account Manager 或 Messaging
   API 皆可設定，上傳選單圖片、設定按鈕動作為「開啟 LIFF」。
3. 既有的 Google OAuth（Client ID、`GOOGLE_CLIENT_ID` 等）設定不變，
   只是使用者從全體員工縮小成管理員 2 人，不需要異動。

## 十、待確認／風險

- **通知則數預算**：目前設計（每週一次、只發未交者）用量很小，但
  這是「未來每加一種通知都要重新盤算月 200 則額度」的第一步，建議
  之後每次要加新的自動通知功能時，先估算月用量再實作。
- **未綁定 LINE 又未提交的員工**：見 4.2，目前先用「管理頁標示、
  管理員手動處理」的方式暫時繞過，不是完整解法。如果這種情況常發生
  （例如新人入職但還沒用過一次系統），可能需要額外設計「入職當天
  自動私訊邀請開通」的流程，這次先不做。
- **LIFF 在「不是用 LINE App 開啟」時的行為**（例如被分享到瀏覽器直
  接打開）：LIFF 的自動識別機制依賴 LINE App 的登入狀態，用一般瀏覽器
  打開理論上還是能動（LIFF SDK 支援 External Browser 模式，會跳出
  LINE 登入頁），但體驗上會退化成類似之前 LINE Login 的同意畫面。
  這是預期內的降級行為，不算 bug，測試時建議直接在手機 LINE App 裡
  測試主要路徑。
- **舊的「群組全員 mention」邏輯拿掉後**，如果店主之後還是想要「群組
  裡能看到大家都交了沒」這種公開透明感，屬於管理面的取捨，不是技術
  限制，需要的話再另外評估要不要保留一個「彙總、不點名」版本的群組
  公告（例如「本週已有 8/11 人提交」這種不具名的進度訊息）。
